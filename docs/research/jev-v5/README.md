# Jev 第五轮：批量 Choice、有限背景与引用提取修复

2026-09-22。本轮新增四组真实配对实验，修复实际提取缺陷，并将无背景批量 Choice 做成**默认不启用的可选策略**。结论是本样本输入用量下降、支持判断未观察到退化；不能宣称延迟已经稳健改善，也没有解决此前的指代漏判。

## 官方资料与实验动机

重新读取官方 API、模型表、fan-out 和构建指南，4 份快照及时间/哈希见 [sources-batching.json](sources-batching.json)。官方说明多题独立并行、题目 ID 不参与推理、structured instructions 可带每题数据；64k 限制覆盖 state 与全部题，32k 覆盖 state 与最长题。官方说增加问题通常对延迟影响较小，**未保证改变输入表示后概率等价，也未保证本项目的速度和费用比例**。

因此没有将所有文档合并成共享 state。批量候选的 state 为 `{}`，每道题的 instructions 内只有其自己的声明与所引来源；任何另一题的来源都不进入这一题的输入。有限背景只作为第四个研究候选，未用于已接入的批量实现。

## 冻结设计与标注

[`evals/jev_v5/batching`](../../../evals/jev_v5/batching) 包含 36 个案例、70 个引用单元：12 个已知 v4 开发案例、24 个新测试案例（8 个家族、48 单元，24 支持/24 不支持）。新案例覆盖版本、实体、条件、否定、未知地点、数值单位、英文指代，以及正确背景配错误引用、背景中的 supported 指令。

标签由主助手调用前编写，另一助手只读复核二元支持标签，未发现误标；**不是独立人工标注**。不支持既包括矛盾也包括证据不足，不冒充三分类金标。家族内变体相关，统计按家族重采样。原始数据 SHA256：`3c0444a19598fcb973b4a4d92cdb222572969c1a9d880264a4f6f60aa6728af4`。

[protocol.json](protocol.json) 在调用前冻结规则、模型 `jev-1.13.0`、0.8 支持阈值和 300,000 输入 token 预算；之后未按测试结果调提示词或阈值。四种模式按案例打乱执行顺序，均为新的真实调用，没有用缓存时间冒充在线时延：

| 模式 | 请求形式 | 能归因什么 |
| --- | --- | --- |
| A current | 每单元一请求，共 Choice + 2 Noul，沿用生产逐段诊断 | 当前实现对照 |
| B structured_single | 每单元一请求，仅 Choice，claim/来源放 structured instructions | A→B 同时改变题数和表示，不能只归因于删除 Noul |
| C batch | B 的题目内容、ID、空 state、版本完全相同，只合为一请求 | B→C 隔离批处理影响 |
| D batch_background | C 另加前文最多240字符，明确只解释指代、不能作证据 | 测是否补救指代与是否引入误支持 |

## 真实结果

144 个案例×模式回执完整落盘：[batching.jsonl](results/batching.jsonl)。212 次客户端调用尝试取得 209 个成功响应，另 3 次超时，分布在 B 的 2 个案例中；“客户端尝试”并非供应商收到请求数的独立审计。每次遇到失败都停止新增案例，检查后仅继续未尝试配对，未重试失败项。首次运行代码已保存在 [run-code.json](run-code.json) 索引下。

| 新测试集（24案例、48单元） | A current | B structured_single | C batch | D batch_background |
| --- | ---: | ---: | ---: | ---: |
| 完成语义判断的单元 | 48 | 46 | 48 | 48 |
| 24个正确单元获得支持 | 24 | 24 | 24 | 24 |
| 完成判断的错误单元被误支持 | 0/24 | 0/22，另2个超时 | 0/24 | 0/24 |
| 案例耗时P50（秒） | 0.765 | 0.743 | 0.702 | 0.712 |
| 案例耗时P95（秒） | 0.969 | 1.002 | 0.834 | 0.833 |
| 服务端报告输入token | 35,217 | 23,810 | 18,633 | 24,870 |

A→C 在这24个完整配对上输入用量减少 **47.09%**。B 有失败，不能直接比较总用量作为等任务成本；只取23个双边成功配对，B为23,810 token，C为17,853 token，减少 **25.02%**。均使用公开输入单价估算，不包含未知计费的超时，也不是账户最终账单。

B→C 成功配对的平均延迟差为 −0.0345 秒，按8家族bootstrap的95%区间 **[−0.0948, +0.0079]**，包含零。成功配对全部46个单元的 Choice 类别与0.8支持信号均无差异。本轮因此支持“观察到输入用量下降”，不支持“已证明显著加速”或长期 SLA。

开发集 A 与 C 均支持9/11个正确单元，没有误支持；D仅支持8/11。两个 `same document/source` 的旧漏判没有恢复，D还漏过了一条审批流程陈述。**有限背景方案本轮不采用**。新测试集虽未观察到背景引入误支持，也不足以抵消其无收益、额外输入用量与更复杂证据边界。

主实验已报告156,164输入token，估算 **$0.006558888**；计入超时保留的7,240 token预留后，预算记账163,404 token、**$0.006862968**。失败、支持信号差异、分母和费用口径见 [batching-summary.json](results/batching-summary.json)。

## 独立代码审查后的实际修复

引用提取升级为 `trailing-citations-v2`：

- 编号列表的 `1.` 不再算作未引用句子。
- `The U.S. limit is 600[1]`、`e.g.` 等常见缩写不会被截掉前面的实体/限定语；存在句末歧义的情形明确记为未覆盖。
- `[1], [2]`、中文逗号/顿号引用组正确归到同一声明，不再提交纯标点声明。
- `Limit is 600[1] per second` 这类非尾随引用不会只提交丢失单位的前半句；直到明确的新句边界才恢复评估。

这些是保守的有限语法处理，不是完整英文/Markdown解析。歧义拒绝可能降低覆盖率，但不会假装缩短后的句子代表原声明。24项新增行为用例覆盖这些问题；30份v4冻结答案的单元提取保持一致，历史数据和回执未改。

## 可选批量实现与真实接入

新模块 [`jev_citation_batch.py`](../../../backend/app/modules/generation/jev_citation_batch.py) 与实验C的题目逐字段一致。最多8个单元，复用同一个worker的Jev客户端/额度。每单元先校验完整来源、文本类型、长度；不合格者独立保留原因，其余单元一次请求。整批失败时所有参与单元均为未评估，**没有自动逐单元付费重试**。

相对于原策略，批量减少请求数，也把失败影响范围扩大到整批；大请求会触发客户端大小限制，不能隐藏为部分成功。共享输入usage只记一次，位于顶层 `batch_metadata`；单元只返回 Choice，不伪造已移除的两个 Noul 或 `factorized_support_signal`。

```dotenv
# 主开关仍默认关闭；以下为明确选择批量诊断时的配置
JEV_CITATION_MODE=shadow
JEV_CITATION_STRATEGY=batch_choice
JEV_TIMEOUT_S=3
TYPESAFE_API_KEY=<安全注入>
```

默认策略仍为 `per_unit`，不改变已经验证的旧路径；回滚只需改回 `per_unit` 或将主开关设为 `off` 并重启进程。批量策略也只提供诊断，不自动改写、认证或拒绝答案。

实际接入证据：

| 验证 | 实际结果 |
| --- | --- |
| 8单元容量/来源隔离 | 1次真实调用评估全部8个单元，4正例/4数字变异均符合预期，0.768秒，2,395输入token |
| 实际普通生成→批量诊断 | Kimi生成600次限额及正确引用；1单元实际评估，诊断0.683秒、617输入token |
| 实际流式生成→批量诊断 | 审批链、48小时和365天的3单元实际评估，诊断0.719秒、1,214输入token |

原始回执见 [eight-unit-live.json](results/eight-unit-live.json) 和 [generation-batch-live.jsonl](results/generation-batch-live.jsonl)。流式首个正文在13.665秒，引用在16.383秒，DONE在17.102秒，诊断发生在正文和引用之后。不同轮次的生成答案/网络状态不同，不能把该时间与v4直接相减宣布加速。

这三次额外Jev调用取得4,226输入token，估算$0.000177492。本轮总已知Jev费用约 **$0.006736380**；包括主实验未知计费预留的预算记账约 **$0.007040460**，不含Kimi。真实生成使用冻结检索输出，本轮未重跑入库、检索、HTTP或浏览器验收。

## 评估器续跑保护与复现

独立审查发现旧评估器存在“进程中断时已发请求未落盘”的预算缺口。**此次144个回执是在受控正常进程完成/超时后写入的，没有声称旧实验事前具备后加的机制**；归档执行代码可核对。

更新后的评估器只允许新输出路径开启live：事前 execution manifest 锁定评估器、客户端、候选、规则代码哈希及模型/阈值/超时，整个live过程持有非阻塞文件锁；每组付费调用前持久化pending，回执fsync后清除。发现未决pending时停止，即使续跑参数也不能绕过。其作用是检测未决工作，**不是自动恢复计费或确认账户账单**。历史回执无事前manifest，只允许离线复算。

```bash
# 离线复算历史实验，不需要凭证
python backend/scripts/evaluate_jev_batching.py

# 新真实实验：输出路径必须全新，自动生成 execution/pending/lock 旁文件
python backend/scripts/evaluate_jev_batching.py --live \
  --provider-env "$PROVIDER_ENV" --key-file "$KEY_FILE" \
  --output /tmp/jev-batching-new.jsonl --report /tmp/jev-batching-new.json

python backend/scripts/verify_jev_generation.py --strategy batch_choice \
  --provider-env "$PROVIDER_ENV" --key-file "$KEY_FILE" \
  --output /tmp/jev-batch-generation-new.jsonl
```

最终相关回归 **154项通过**，包含26项批量合同测试和9项评估器续跑/统计测试。来源/数据/回执校验和代码指纹见 [verification.json](results/verification.json)。局限包括小规模自编且相关的样本、生产分布未知、批次部分可用性降低、缩写/Markdown覆盖有限、业务概率未校准。结果支持继续受控使用可选批量诊断，不支持替换Qwen重排或自动引用认证。
