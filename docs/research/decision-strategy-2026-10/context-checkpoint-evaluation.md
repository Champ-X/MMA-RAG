# 最终上下文证据检查点：冻结诊断评测

验证日期：2026-10-09。新策略为 `visible-evidence-checkpoint-v1`，原生提示为 `candidate-evidence-role-v1`。Jev 与 Luna 在 8 条人工明确标注的目标补证中分别选中 5 / 4 条，没有误补；百炼选中 3 条并误补 1 条。在自然问题池中，尚未证明新策略优于同样多给两个位置的 Qwen-next2。这里记录工程覆盖、功能行为和固定标注指标，不作为通用准确率或全面效果提升的结论。

## 结构变化与边界

原 `incremental-evidence-v2` 将候选同时与完整基线比较，要求直接有用和全局增量两个 Noul 信号都达到 0.85。它会整轮跳过超过 12,000 字的基线；而原文中已有的事实可能被生成上下文的 500 字格式化上限隐藏。

新接口 `select_context_evidence(client, query, candidates, visible_context, ...)` 在原上下文固定之后使用。模型只判断候选原文对于查询的角色：回答、限定条件、反证、范围不适用、不相关或不确定；不判断全局新颖性。当前采用的门槛是被选中有效角色的原生概率至少 0.8，不是正确率认证。

- 最多扫描 80 个已授权候选，单个原文最多 80,000 字；选取完整连续段落，每段最多 4,000 字，不生成摘要、不切断段落、不请求原媒体。
- 候选缺少 `content_type` 时沿用项目模态推断；明确图片/音频/视频和相应派生 payload 不作为文档处理。
- 只对生成器实际看到的文本做本地重复抑制；容忍已有格式化器把中文句读转为空格的显示变化，保留数字、百分号、单位和否定。
- 一个原生批次最多 10 个候选、40,000 UTF-8 输入字节、3 秒总时限。整批完整校验后才返回最多两条，失败不重试、不换模型、不部分采用。
- 追加顺序沿用候选顺序，原分数字段不变。原 chunk ID 可以已经在基线中；它未显示的段落仍可作为新的引用材料。
- 返回 `excerpt`、`span_start/end`、原文/段落 SHA-256、`partial_source`；offset 单位为 Python Unicode code point。`partial_source` 不代表阅读全文，不能据此推断全文不存在某项信息。
- 诊断区分 `accepted_ids`、最多两条的 `proposed_ids` 和实际交给调用方的 `added_ids`；调用方追加失败时仍需以最终上下文实际包含的材料修正 applied 状态。

## 在模型输出前固定样本

协议为 [`evals/decision_checkpoint_v2/protocol.json`](../../../evals/decision_checkpoint_v2/protocol.json)，SHA-256：`762923ae964476b8374ad52bc660e07f9a3a342f95fa38cd05ed8726eb3165c7`。

从现有 C-MTEB/T2Reranking 冻结池读取自然查询及原始 qrels，只使用历史 Qwen 分数重建当前 top-10 基线。240 个 test query 中有 35 个漏掉至少一个正标签材料；排除之前 12 题 assist pilot 后剩 34 个。先按固定 SHA 排序，再按基线长度和候选数量匹配已覆盖的控制问题，选首 10 对，共 20 题。选择不读取 Decision 预测。完整 34 对名册保存在 `cohort.json`。

这些查询曾用于旧重排研究，因此称为诊断样本，不能重新称为未见确认性 holdout。原始 T2 源 parquet 当前未保存在本 checkout 的 `data/jev-v2/`；另建真正未见样本需要重新获取有固定哈希的来源并排除历史规范化 query。

另固定 7 个手写功能案例，共 8 条预期补证，覆盖已保留 chunk 第 500 字之后的信息、部分问题回答、错误实体、错误版本、否定答案、反证、纯重复、长基线与长 chunk 完整段落。它们是功能检查，不代替自然检索评价。

## 自然问题池结果

基线平均 Recall 为 0.700。Recall 按唯一文档 ID 计算；补入已存在 chunk 的隐藏段落不会人为增加 Recall。旧/新策略均保留原证据，不更改 top-10 和原分数。

| 方案 | 新增材料 | 其中正 qrel 材料 | 找回缺失正 qrel | 最终 Recall |
|---|---:|---:|---:|---:|
| Jev · 旧 v2 | 0 | 0 | 0 | 0.700 |
| Jev · 新检查点 | 15 | 4 | 1 | 0.725 |
| 百炼 · 旧 v2 | 1 | 0 | 0 | 0.700 |
| 百炼 · 新检查点 | 22 | 4 | 3 | 0.775 |
| Luna · 旧 v2 | 2 | 1 | 1 | 0.725 |
| Luna · 新检查点 | 11 | 4 | 1 | 0.725 |
| Qwen-next2，同样最多追加两条 | 40 | 3 | 3 | 0.775 |
| recall-next2，同样最多追加两条 | 40 | 4 | 4 | 0.800 |

两个无 Decision 对照都从相同已有池选择，使用相同段落边界和可见文本重复抑制。它们表明“增加材料数量”本身就能提高覆盖；本轮新检查点没有在固定 qrels 上超过简单等槽位对照。新策略相对旧策略的 paired query bootstrap 95% CI 分别为 Jev `[0.000, 0.075]`、百炼 `[0.000, 0.150]`、Luna `[-0.075, 0.075]`，均不足以建立稳定优势。该 20 题还是经过 headroom/matched-control 筛选的条件分布，不代表正常用户请求中的收益率。

### 固定 qrel 的语义局限

按原始 qrels 计数，不在看过输出后重新标注。负标签也不能直接当作“错误证据”的真值。例如 `t2v2-4661` 查询“风居住的街道表达什么”：

- 正标签 `-13` 是较长散文，后部描述二胡与钢琴的“悲切凄清”“痛苦无奈”。
- 正标签 `-05` 大部分是网友相识回忆。
- 负标签 `-11` 直接描述“二胡的忧伤胜过钢琴的浪漫”“两个永远不能在一起的恋人”，百炼将其判为 answer，概率 0.88。

该负标签段落明显包含可回答音乐情绪的问题信息。评测仍保留其负标签计数，例子只说明这种 qrel 不能充分衡量局部补证效用。T2 条目也没有真实的独立来源身份，不能用合成的 `file_id=doc.id` 证明多源交叉验证。

## 功能行为

| 功能案例 | Jev 新检查点 | Luna 新检查点 | 百炼新检查点 |
|---|---|---|---|
| 基线第 500 字后的退款事实 | 正确补入 | 未补入 | 正确补入 |
| 两项借阅期限/续借条件 | 选中期限，漏条件 | 选中条件，漏期限 | 选中期限，漏条件 |
| 新版本不支持 JSON / 未解密限制 | 两条均漏 | 两条均选中 | 两条均漏 |
| H12 的反证，H13 为干扰项 | 正确反证，无误补 | 正确反证，无误补 | 正确反证，同时误补 H13 |
| 已可见的纯重复 | 零调用，不追加 | 零调用，不追加 | 零调用，不追加 |
| 长可见基线下的取消条件 | 正确补入 | 未补入 | 未补入 |
| 长 chunk 的完整相关段落 | 正确补入 | 未补入 | 未补入 |
| 8 条预期补证合计 | **5 正确 / 0 误补** | **4 正确 / 0 误补** | **3 正确 / 1 误补** |

同一新功能集上，旧 v2 的 Jev/Luna 都是 0 条正确、0 条误补；百炼为 1 条正确、1 条误补。百炼把 H13 当 H12 证据是明确的适用范围错误，新检查点选中概率为 0.85，旧 v2 也误收了该项。不能把高原生概率视为正确的来源适用性。

还有有效角色之间概率分摊的问题：回答/条件/反证都是可用角色，单个最大角色没有达到门槛未必意味着总可用性低。当前没有根据本批结果改门槛、合并概率或补跑；这些只能作为下一版假设，需另冻结且保留独立样本。

## 调用、预算和可重现性

三家新检查点各有 26 个非空批次，均完整返回原生 Choice；另一个纯重复案例确定性跳过，未调用模型。旧 v2 的 Jev 有 3 次 stage timeout，百炼 1 次，Luna 4 次 timeout 和 2 次 HTTP 502；其余跳过和失败均保留分母。

| 路由 | 旧 v2 完成 stage 的中位耗时 | 新检查点完成 stage 的中位耗时 | 旧 / 新成功请求报告 input tokens |
|---|---:|---:|---:|
| TypeSafe Jev | 1.834 s | 1.020 s | 499,423 / 215,348 |
| 百炼 | 0.979 s | 0.503 s | 403,701 / 153,793 |
| OpenRouter Luna | 2.216 s | 1.081 s | 421,758 / 186,332 |

上述耗时只描述本机此次运行，完成 stage 的中位数排除了失败/跳过，不能当总体 SLA；失败数量已经单列。成功请求 input token 不包含超时请求的未知计费，不等于完整费用。

每个 provider/policy 使用独立客户端，保守预算固定为 6,480,000 token reservation（27 个案例 × 最多 4 请求 × 每请求 60,000 上界）；实际逐请求仍受 3 秒总时限和大小约束。没有因上一策略消耗预算而阻断下一策略，也没有自动重试。保存设置和冻结源码在运行前后哈希一致，没有检索/重新索引或生成最终回答。
