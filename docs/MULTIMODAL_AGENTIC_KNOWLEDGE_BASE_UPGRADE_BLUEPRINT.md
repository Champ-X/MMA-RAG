# MMA-RAG 多模态 Agentic 知识库升级蓝图

> 文档定位：产品与能力升级方案，不展开具体技术选型和工程实现。
>
> 调研基线：MMA-RAG 当前代码与文档、Tencent WeKnora、LLM Wiki、Open Knowledge Format、RAGFlow、Dify、NotebookLM、GraphRAG，以及 DeerFlow、LangGraph、pi、OpenAI Agents SDK 等 Harness/Runtime 设计。
>
> 更新时间：2026-07-18（深化版：补充 Agent Harness、任务恢复、范围隔离、上下文治理与能力分级）

## 0. 核心结论

MMA-RAG 当前已经拥有一块有价值、不能在升级中损失的底座：它不是给纯文本 RAG 外挂图片入口，而是分别处理文档、图片、音频和视频，能够自动选择知识库，执行 Dense、Sparse、视觉、音频、视频多路召回，完成融合、精排和可回放的多模态引用。

它当前更准确的产品形态仍然是：

> **一次查询驱动的一次性多模态答案引擎。**

升级目标不应只是给这条流水线增加一个 Planner，也不应把产品改造成另一个 WeKnora，而应将它升级为：

> **能够持续接入和理解多模态资料，将原始证据编译成可演化知识，围绕复杂目标自主研究，产出可验证成果，并在授权下推动后续行动的通用知识工作平台。**

推荐产品名可继续沿用 Nexus，新的品类定义为：

> **Multi-Modal Agentic Knowledge Base**
>
> 多模态 Agentic 知识库 / 多模态知识工作空间

这一升级的本质，是完成六个转变：

| 当前形态 | 目标形态 |
|---|---|
| 以文件和向量切片为中心 | 以证据、知识对象、任务和成果为中心 |
| 用户提问一次，系统检索一次 | 系统围绕目标持续查找、核验和调整 |
| 多模态内容最终主要转成文字描述 | 原始页面、区域、音频片段、视频场景都可成为一等证据 |
| 答案留在会话中 | 结论和成果可沉淀、复用、更新和追踪 |
| 被动等待用户查询 | 主动发现冲突、过期、缺口、影响与待办 |
| 模型停止生成即视为完成 | 系统明确区分完成、部分完成、证据不足、待确认和失败 |

目标不是“让每个问题都跑 Agent”，而是建立双路径：

```text
简单、明确问题 ──→ 快速多模态 RAG ──→ 秒级可信回答

复杂、开放目标 ──→ Agentic Research ──→ 多步研究、验证与成果
                            │
                            ▼
                 活知识 / Wiki / 关系 / 时间线
                            │
                            ▼
                     Studio / 行动 / 复用
```

旧能力成为 Fast Path，新能力成为 Research Path；二者共享同一套原始证据和权限体系。这是“保留优势且取得综合正收益”的第一原则。

### 深化后的六个新增判断

1. **必须把 Agent Harness 作为产品能力**：规划之外还要有预算、停止、恢复、审批、错误处理和结果验收；
2. **双路径需要细化为 L0–L3 执行深度**：从无需检索、快速检索到 Agentic Research 和长时深度任务逐级升级；
3. **每个任务必须有范围胶囊**：本轮文件、知识库、时间、工具和权限范围不能污染后续会话；
4. **长任务需要证据账本与上下文治理**：证据去重、产物外置、摘要可追溯，且摘要永远不能替代事实来源；
5. **Knowledge Space 应采用能力画像**：基础搜索、多模态、Wiki、Graph、研究和行动能力按需组合；
6. **路线顺序应先可靠运行、再自主研究**：任务状态、恢复、权限和结果语义是 Planner 之前的发布门槛。

## 1. 当前产品能力基线

### 1.1 已经形成的核心资产

根据当前仓库的主链路、架构文档和前端交互，MMA-RAG 已经具备以下产品资产。

#### 原生多模态接入

- 文档：PDF、Word、PPT、Markdown、文本、Excel、CSV；
- 图片：视觉理解、Caption、视觉向量和文本向量；
- 音频：转写、语义描述、文本向量与声学向量；
- 视频：分段理解、关键帧、视觉向量、文本描述和时间点；
- 数据来源：本地上传、URL、网页、文件夹、Markdown、热点与媒体来源；
- 可通过飞书渠道使用部分问答能力。

#### 已有检索优势

- 知识库画像和跨知识库自动路由；
- Dense、Sparse、Visual、Audio、Video 多路召回；
- RRF 融合与 Cross-Encoder 精排；
- 支持指定知识库、指定文件和临时附件；
- 对文档、图片、音频和视频引用提供不同的预览或播放体验。

#### 已有可信体验雏形

- 展示意图识别、知识库路由、检索、生成等阶段；
- 回答带来源编号；
- 引用可以回到文档、图片、音频或视频；
- 有上下文检查器、知识库画像和推荐问题等辅助能力。

这些能力是升级的“不可回退清单”。任何新架构如果让简单问题变慢、让音视频召回变弱、让引用失去可回放性，均不应被视为成功升级。

### 1.2 当前产品上限

当前系统主要执行以下固定链路：

```text
查询理解
→ 知识库路由
→ 一次混合检索
→ 一次精排
→ 一次上下文构建
→ 一次回答生成
```

代码虽然已经识别复杂问题和子查询，但复杂度尚未真正改变任务执行方式；生成阶段也主要围绕一次上下文完成一次最终回答。因此系统可以“搜得丰富”，但还不能围绕一个目标持续工作。

主要产品缺口如下。

| 维度 | 当前表现 | 用户感知的上限 |
|---|---|---|
| 任务 | 每轮问答基本独立 | 复杂研究需要用户反复追问和人工拼接 |
| 知识 | 文件、切片和向量结果为主 | 无法直接浏览项目、人物、决策、结论和关系 |
| 多模态 | 检索原生，生成侧主要使用描述或转写 | 图表细节、图像区域、语气、动作和时序容易丢失 |
| 引用 | 校验引用编号是否存在 | 尚不能证明每条主张真正得到证据支持 |
| 生命周期 | 上传后成为静态资料 | 不知道内容是否过期、冲突或被替代 |
| 成果 | 结果主要停留在聊天中 | 研究过程和结论难以复用与持续维护 |
| 记忆 | 短会话上下文 | 服务重启、长任务、跨会话经验和用户偏好难以延续 |
| 治理 | 有可选用户字段和数据隔离雏形 | 无法支撑组织协作、细粒度授权和行动型 Agent |
| 质量 | 以功能运行和人工体验为主 | 无法证明升级没有损失原有检索质量 |

### 1.3 代码审阅中的关键依据

本方案的判断来自当前仓库，而不是只依据 README 中的产品命名：

- [检索主链路](../backend/app/modules/retrieval/service.py) 展示了预处理、路由、混合搜索和精排的一次执行流程；
- [生成服务](../backend/app/modules/generation/service.py) 主要构建一次上下文并调用一次最终生成；
- [上下文构建](../backend/app/modules/generation/context_builder.py) 负责把不同模态整理成文本上下文和可展示引用；
- [聊天 API](../backend/app/api/chat.py) 当前使用进程内会话状态，并明确标注生产环境应使用持久化存储；
- [知识库服务](../backend/app/modules/knowledge/service.py) 需要兼容对象存储与向量库中的知识库 ID 不一致，元数据仍带有原型期控制面的特征；
- [架构文档](MMA_ARCHITECTURE.md) 说明当前精排主要以文档文字、图片 Caption、音频 Transcript/Description 和视频 Description 参与模型评分；
- [当前主导航](../frontend/src/components/layout/AppLayout.tsx) 仍集中在聊天、知识库、架构和设置，没有任务、Wiki、成果、治理等产品空间；
- 当前仓库未形成覆盖摄取、跨模态检索、引用支持和 Agent 任务的系统化回归评测集。

## 2. 目标产品定义

### 2.1 产品不是“RAG + Agent”，而是知识闭环

升级后的系统需要持续完成以下闭环：

```text
接入信息
→ 理解多模态内容
→ 形成原子证据
→ 编译成活知识
→ 围绕目标自主研究
→ 核验结论
→ 生成成果
→ 推动行动
→ 从反馈中更新知识与经验
```

用户不再只问“文件里有什么”，还可以交付一个目标：

> 综合这些文档、设计稿、会议录音、演示视频和数据表，解释方案为什么变化，找出仍有争议的部分，形成一份带证据的决策备忘录。

系统应自行完成资料查找、上下文展开、跨模态比较、冲突识别、证据补充、结论核验和成果组织。用户看到的是清晰的工作进展和证据，不是模型的隐藏思维过程。

### 2.2 九个通用产品对象

为了应对通用场景，产品不能以“用户研究”“项目复盘”等垂直任务作为底层结构。建议用九个通用对象构成产品语言。

| 对象 | 含义 |
|---|---|
| Space | 围绕项目、产品、客户、主题或个人研究组织知识的空间 |
| Source | 原始文件、网页、系统记录、数据流或外部知识源 |
| Evidence | 可精确定位的页面、段落、单元格、图片区域、音频片段或视频场景 |
| Knowledge Object | 人物、概念、事件、决策、需求、风险、指标、过程等可复用知识 |
| Claim | 可以被支持、反驳、确认、过期或替代的明确主张 |
| Task | 有目标、范围、进度、证据、预算、停止原因和结果状态的持续性工作 |
| Artifact | 报告、Wiki 页面、表格、时间线、图谱、PPT、音视频摘要等成果 |
| Action | 创建、更新、发送、发布、提醒、触发等可审计操作 |
| Policy | 权限、风险、审批、保留、质量和发布规则 |

场景模板只是在这些对象之上的预设：竞品研究、学习助手、技术调研、项目复盘、客户知识、合规检查都可以由同一套通用能力组合，而不是分别开发一套产品。

### 2.3 四种用户工作方式

产品应提供一个统一入口，默认由系统自动选择，也允许用户显式切换。

#### 快速问答

适合明确事实、定位原文和简单总结。继续复用当前高效多模态 RAG，强调速度、准确和引用。

#### 深度研究

适合比较、解释、归因、多跳、跨知识库和开放目标。系统建立任务，持续查找、验证和更新阶段性结果。

#### 浏览知识

用户通过 Wiki、人物、项目、概念、关系、时间线和知识问题直接浏览，不必每次都从聊天框开始。

#### 创作与推进

用户选择知识和证据，生成成果；在授权下，把成果转成任务、更新、发布或后续跟踪。

这四种方式共享同一知识底座，不是四套割裂产品。

## 3. 必须坚持的升级原则

### 原则一：增强而非替换

现有多模态检索是产品差异化基础。Fast Path 必须长期保留，Agent 只在复杂任务中介入。

### 原则二：原始证据与编译知识并存

Wiki、图谱和摘要适合概念理解、关系导航和跨来源综合；精确数字、原话、最新状态和具体操作仍必须回到原始证据。编译知识不能成为新的事实孤岛。

### 原则三：多模态端到端保真

图片不能只剩 Caption，音频不能只剩 Transcript，视频不能只剩关键帧描述。每种模态的原始结构、时序和定位信息都应保留到检索、推理、引用和成果阶段。

### 原则四：生成内容默认不是事实

产品必须清晰区分：

1. 原始资料；
2. AI 提取的知识；
3. AI 生成的分析；
4. 人工确认的正式知识。

自动生成 Wiki 不能无痕覆盖原文，也不能自动冒充已确认结论。

### 原则五：Agent 必须可控、可停、可恢复

用户需要看到目标、阶段、证据、缺口和待确认事项；可以暂停、继续、改变范围或排除证据。展示可理解的工作过程，不展示模型私有思维链。

### 原则六：主动不等于擅自

系统可以主动发现、建议和生成草稿；涉及正式知识修改、外部发送、删除、公开发布等动作，需要与风险相匹配的审批和撤销能力。

### 原则七：通用原语优先，场景预设辅助

底层能力面向所有行业和任务；上层用预设降低使用门槛。避免把项目演化成只适用于某一业务部门的工作流集合。

### 原则八：每个新能力必须证明净收益

判断标准不是“是否前沿”，而是：

- 是否提升任务成功率或知识复用；
- 是否与现有多模态优势产生协同；
- 是否引入可接受的成本、延迟和治理负担；
- 是否可以按需启用和渐进展开；
- 是否有清晰的质量指标与退出机制。

### 原则九：Agentic 的核心是外部保障，不是更长的推理

真正可靠的 Agent 不能只依靠 Prompt 自律。任务是否可以执行、能否继续、何时停止、是否需要审批、结果是否达标，都必须由模型之外的产品规则控制。

对用户而言，这意味着：

- 任务有明确范围和预算；
- 系统不会无限重复搜索；
- 高风险动作不会被模型自行批准；
- 中断后能够继续，而不是从头重做；
- 预算耗尽或证据不足会返回部分结果和真实原因；
- “模型已经回答”不等于“任务已经成功”。

### 原则十：知识能力按需编译，不追求全量开启

并非每个知识空间都需要 Wiki、图谱、深度视频分析和长期记忆。系统应根据资料形态和使用目标推荐能力组合，并允许逐步增强：先可搜索，再结构化，再编译知识，最后进入验证和发布。

这既控制成本，也减少低质量自动生成知识对原始检索的干扰。

## 4. 目标能力蓝图

## 4.1 从多模态文件升级为多模态原子证据

当前系统已经能处理多模态，下一步不是继续增加文件类型，而是提高每种模态的证据粒度和可推理性。

| 模态 | 当前可用基础 | 升级方向 | 用户得到的效果 |
|---|---|---|---|
| 文档 | 段落、图片、表格内容和页面信息 | 保留章节、页面布局、表格单元格、图表、脚注、批注、版本差异 | 可回答“哪个版本、哪一页、哪个数据点发生了变化” |
| 图片 | Caption、CLIP 与文本语义 | 对象、OCR 块、图表区域、UI 组件、局部区域、空间关系和版本对比 | 可按区域检索和引用，不再只描述整张图 |
| 音频 | 整体转写、描述和声学向量 | 说话人、时间段、主题、问答、决策、分歧、语气和片段级证据 | 可直接定位谁在什么时候表达了什么 |
| 视频 | 场景理解、关键帧和时间点 | 章节、场景、镜头、动作、屏幕操作、语音、OCR 与事件顺序 | 可研究操作过程和前后关系，不只搜索关键帧 |
| 表格/数据 | 文本化内容 | 单元格、指标、口径、公式、时间范围和可复算结论 | 数字结论可以核对来源和计算方式 |

建议为每种证据提供统一的“证据卡”：

- 内容摘要；
- 原始位置；
- 所属来源与版本；
- 时间范围或空间区域；
- 相关人物、概念和事件；
- 权限和有效期；
- 可播放、可缩放或可跳转的原始内容；
- 被哪些主张和成果使用。

最终效果是：多模态不只是可检索的文件类型，而成为 Agent 可以组合、比较和核验的证据语言。

## 4.2 建立自适应的 Quick RAG 与 Agentic Research 双引擎

### Quick RAG

适用情况：

- 单一事实；
- 明确定位；
- 简单总结；
- 已知范围内的问答；
- 对延迟敏感的交互。

它应继续使用当前成熟的知识库路由、多路召回、融合、精排和引用能力。

### 对现有检索的增强要求

保留 Fast Path 不等于冻结现有检索。升级应围绕用户可感知质量继续增强：

- **语义与精确检索互补**：概念问题使用语义召回，人名、数字、错误码和原话使用精确搜索；
- **多视角查询可追溯**：复杂表达可以生成多个视角，但每条证据都记录由哪个子问题命中，避免查询扩展失控；
- **先小粒度命中，再补完整上下文**：既保证定位准确，也减少断章取义；
- **结果去重与多样性**：避免多个相似片段占满上下文，同时保留不同模态和不同来源的重要证据；
- **模态感知降级**：某一路模型或索引暂时不可用时，继续使用其他检索能力并向用户说明限制；
- **版本和时间优先级**：查询“最新”“当时”“变化原因”时，检索必须考虑有效时间和版本替代关系；
- **范围一致**：指定文件、知识库、标签和时间的查询，在改写和补检索后仍不得越出原范围；
- **召回、排序与验证分工**：高相关不等于被证据支持，最终可信性由独立验证判断。

### Agentic Research

适用情况：

- 问题包含比较、解释、归因或方案生成；
- 需要跨文件、跨知识库或跨模态；
- 首轮证据可能不充分；
- 需要核验冲突、追踪版本或形成完整成果；
- 是一个持续任务而非一轮回答。

系统在产品层面应具备：

1. 把目标拆成可理解的研究步骤；
2. 根据每一步选择适合的知识表面；
3. 打开完整上下文，而不是只消费 Top-K 摘要；
4. 根据中间发现继续搜索；
5. 判断证据是否足够；
6. 发现冲突和缺口时改变研究方向；
7. 在预算或证据边界内停止；
8. 输出结论、证据、限制和未解决问题；
9. 保存任务，允许暂停和恢复。

用户看到的工作过程应该是：

> 已检索相关资料 28 份；正在比较三个版本；发现两条时间线不一致；仍缺少正式审批记录；已基于现有证据形成临时结论。

而不是暴露模型内部推理文本。

### 自动路由的产品规则

- 默认“自动”：系统判断 Quick 或 Research；
- 用户可显式选择“快速”或“深入”；
- Quick 发现证据不足时，可以建议升级为 Research；
- Research 发现问题简单时，可以直接走 Fast Path，避免成本浪费；
- 相同请求应支持“快速答案”和“深入报告”两个结果层级。

### 四级执行深度

双引擎是产品形态，内部还应有更细的执行深度，避免“简单问答”和“重型研究”之间只有一次跳变。

| 级别 | 执行方式 | 典型请求 | 产品目标 |
|---|---|---|---|
| L0 直接处理 | 不检索或只使用当前明确上下文 | 改写、翻译、整理用户刚提供的内容 | 不制造无意义检索成本 |
| L1 快速检索 | 一次多模态混合检索与回答 | 明确事实、定位原文、单文件总结 | 低延迟、稳定、可引用 |
| L2 Agentic Research | 多步查找、补读、比较和验证 | 跨文件分析、版本比较、原因解释 | 提高复杂任务完成率 |
| L3 深度任务 | 长时研究、外部工具、人工确认或成果交付 | 开放研究、高风险结论、行动任务 | 可恢复、可审批、可交付 |

系统可以根据证据质量逐级升级，也可以在发现任务比预期简单时降级。升级原因应对用户可见，例如“首轮证据覆盖不足”或“发现来源冲突”，避免用户只看到耗时突然增加。

### 任务范围胶囊

每个任务都应明确本次允许使用的范围：Space、知识库、文件、来源、标签、模态、时间范围、外部工具和权限快照。用户通过选择文件或 `@` 某个知识源形成的范围，只约束当前任务，不应悄悄变成长期偏好，也不能在后续会话中造成范围污染。

任务页需要始终回答：

- 当前正在研究什么；
- 可以搜索哪些资料和工具；
- 哪些来源因权限不可用；
- 是否允许联网或调用外部系统；
- 范围在任务过程中是否发生过变化；
- 最终结论覆盖的是哪个时间点和权限快照。

### 任务结果不只分成功和失败

研究任务应使用用户能够理解的结束状态：

| 状态 | 含义 | 用户获得什么 |
|---|---|---|
| 已完成 | 目标与验证条件均满足 | 完整结果、证据和成果 |
| 部分完成 | 已取得可用结果，但仍有未完成范围 | 已完成内容、未完成项和继续入口 |
| 需要补充信息 | 缺少用户选择或关键资料 | 明确问题和所需材料 |
| 等待审批 | 下一步涉及受控动作 | 动作预览、参数和批准/拒绝入口 |
| 证据不足 | 已达到合理查找边界 | 当前可确认内容、缺口和建议 |
| 预算或时间用尽 | 达到任务约束 | 部分成果、消耗和可继续选项 |
| 已取消 | 用户主动停止 | 已保存证据和可恢复位置 |
| 执行失败 | 出现不可恢复问题 | 失败阶段、已保留成果和处理建议 |

这项设计非常关键：Agent 停止调用工具只代表循环结束，不代表用户目标已经达成。

## 4.3 建立双知识表面：原始证据库 + 活知识层

LLM Wiki 最值得借鉴的不是 Markdown 文件，而是三个产品原则：

- **可编译**：把大量原始资料转成更容易检索和理解的知识页面；
- **可组合**：通过链接、反向链接和主题结构支持跨来源推理；
- **可演化**：研究、反馈和错误可以持续更新知识组织方式。

MMA-RAG 应建立两个互补的知识表面。

### 原始证据库

保存原始文件、页面、片段、区域、时间点、版本和权限，是最终事实依据。

### 活知识层

将原始证据组织成可浏览和可研究的页面：

- 来源摘要页；
- 人物与组织页；
- 概念与主题页；
- 项目与产品页；
- 事件与时间线页；
- 决策、需求、风险、指标页；
- 综合分析页；
- 对比页；
- 索引和目录页。

每个页面都应具备：

- 简介和正文；
- 来源证据；
- 相关页面和反向链接；
- 版本与更新时间；
- 草稿、已确认、存在争议、已过期、已替代、已归档等状态；
- 使用的多模态证据；
- 负责人与审核状态；
- 被哪些研究任务和成果使用。

### 路由原则

| 问题类型 | 优先知识表面 |
|---|---|
| 精确数字、原话、代码、最新状态 | 原始证据 |
| 概念解释、整体理解、主题浏览 | 活知识页 |
| 关系、多跳和历史演化 | 活知识 + 图谱/时间线 + 原始证据回查 |
| 高风险结论 | 多源原始证据交叉验证 |
| Wiki 与原文冲突 | 以最新且有权限的原始证据为准，并创建知识问题 |

这能吸收 WeKnora 与 LLM Wiki 的优势，同时避免 Wiki 取代当前多模态检索。

### Knowledge Space 能力画像

知识空间不应只有“开或关”，也不应默认构建所有派生知识。建议把能力设计成可独立组合的画像：

- 基础搜索：全文、Dense、Sparse 和元数据；
- 原生多模态：图片、音频、视频和页面视觉；
- 精确知识：FAQ、术语、字段和结构化数据；
- 活知识：Wiki、概念、人物、事件和主张；
- 关系推理：图谱、时间线和影响链；
- 深度研究：Agentic Research、外部研究和验证；
- 生产行动：Studio、发布、同步和受控工具。

系统根据资料类型和使用目标推荐画像，例如“快速搜索”“多模态研究”“组织 Wiki”“高可信决策”。高级能力可以后续开启，也可以在收益不足时关闭，而不影响基础搜索。

### 分层就绪状态

资料导入不应只有“处理中/完成”两个状态。一个来源可能已经可搜索，但图谱或 Wiki 仍在生成。建议向用户展示：

```text
已接收
→ 可搜索
→ 已完成多模态增强
→ 已编译为知识
→ 已通过质量检查
→ 已发布
```

每一级都说明当前可用能力和仍在进行的工作。这样既允许用户尽早使用资料，也避免把尚未完成或尚未验证的派生知识误认为正式事实。

## 4.4 从文档级引用升级为 Claim–Evidence 可信体系

当前引用体验已经是良好起点，但“引用编号存在”不等于“引用支持结论”。升级后，每一条重要主张都应成为可检查对象。

一条主张需要回答：

- 主张具体是什么；
- 哪些证据支持；
- 哪些证据反驳；
- 是否遗漏关键来源；
- 信息在什么时间范围内有效；
- 是否来自同一来源的重复转述；
- 结论是事实、推断还是建议；
- 当前可信度与人工确认状态如何。

最终回答可提供两个阅读层级。

#### 简洁结果

只显示结论、关键证据和不确定性。

#### 证据视图

展开后显示主张—证据映射、原始位置、冲突、版本、计算口径和系统查找路径。

系统在以下情况下不应强行回答：

- 没有足够证据；
- 来源相互冲突且无法判断；
- 信息已过期；
- 用户无权查看关键证据；
- 数字无法复核；
- 结论超出资料覆盖范围。

此时应明确返回“当前能确认什么、不能确认什么、还缺什么”。

## 4.5 增加证据工作台

聊天右侧不应只是引用列表，而应成为研究任务的证据工作区。

用户可以：

- 查看文档页面、图片区域、音频片段、视频场景和表格数据；
- 固定重要证据；
- 排除无关或低质量证据；
- 查看同一主张的支持和反对证据；
- 比较两个版本或两个来源；
- 添加人工备注；
- 将证据组合保存为证据集；
- 从证据集生成结论或成果；
- 反向查看某条证据被哪些页面、结论和报告使用。

这会把当前“可点开的引用”升级为“可协作的证据资产”。

### 证据账本与上下文经济

深度任务会反复搜索同一批资料。如果每轮都把完整片段重新塞给模型，成本会迅速膨胀，也会增加重复信息对判断的干扰。建议把任务中的证据保存为独立账本：模型主要使用稳定的证据 ID、摘要和必要片段，需要时再打开原文。

产品需要遵守以下规则：

- 相同证据只保存一次，记录它被哪些子问题召回；
- 再次命中时优先返回短引用和新增信息，而不是重复全文；
- 大型表格、媒体和工具产物保存在工作区，通过引用按需读取；
- 对话压缩时保留目标、范围、计划、已确认事实、开放问题、证据 ID 和成果状态；
- 压缩摘要只用于恢复工作上下文，不能替代原始证据；
- 用户随时可以从摘要回到未压缩的完整任务轨迹。

预期效果是让长任务可以持续推进，同时降低 Token 成本、重复召回和“摘要逐轮漂移”。

## 4.6 建立知识图谱、时间线与空间视图，但不强迫所有查询走图谱

图谱适合表达：

- 人、项目、组织、概念、文档、会议、决策、需求、风险、指标和多模态片段；
- 提出、参与、支持、反对、替代、影响、依赖、引用、发生于和属于版本等关系；
- 跨资料多跳问题；
- 整体主题和群落；
- 决策历史和变化影响。

但图谱构建成本高、容易产生错误，也不适合每一个精确事实查询。因此推荐将图谱设计为：

- 活知识层的关系视图；
- 复杂任务的按需研究工具；
- 时间线、人物页和项目页的组织方式；
- 向量与全文检索的补充，不是默认替代。

用户可以在同一个 Space 中切换：

- 文件视图；
- Wiki 视图；
- 图谱视图；
- 时间线视图；
- 结论视图；
- 多模态素材视图。

## 4.7 从静态资料库升级为活的知识系统

每个知识对象和主张都应拥有生命周期：

```text
AI 提取 / 草稿
→ 待验证
→ 已确认
→ 存在争议
→ 已过期
→ 已被替代
→ 已归档
```

系统持续发现以下知识问题。

### 过期

旧方案仍被报告和培训材料引用，但已有新版本。

### 冲突

不同会议或文档对日期、责任人、指标口径或决策给出不同结论。

### 证据不足

重要结论只有一次转述，没有原始数据或正式记录。

### 实体混淆

不同名称可能指向同一人物、产品或概念，也可能被错误合并。

### 重复与孤立

多个页面描述同一主题，或页面没有来源、链接和使用场景。

### 缺失

高频问题没有答案；某项决策没有原因；某个关键流程没有负责人；重要视频尚未被结构化。

### 处理异常

某些页面 OCR 质量低、音频未识别说话人、视频场景解析失败、数据源长期未同步。

知识健康中心应提供：

- 问题列表和影响范围；
- 严重程度与推荐处理方式；
- AI 修复草稿；
- 人工确认、忽略、合并、拆分或重新处理；
- 修复前后差异；
- 完整审计记录。

## 4.8 增加 Knowledge Librarian：持续整理，而非只做问答

建议增加一个面向整个知识空间的“知识馆员”能力。它不是独立聊天人格，而是一组可控的后台知识维护任务：

- 为新增内容建议归属主题；
- 建立或修复页面链接；
- 合并重复概念；
- 标记孤立页面；
- 检查来源和引用；
- 发现知识缺口；
- 生成待确认的页面更新；
- 识别可沉淀的经验；
- 检查成果是否因源资料变化而过期。

知识馆员只能提出建议或生成草稿；对正式知识的修改遵守空间策略和审核流程。

## 4.9 建立多层记忆，但严格控制“什么值得记住”

不应把每轮聊天全部向量化并称为记忆。建议区分四类：

| 记忆 | 内容 | 使用方式 |
|---|---|---|
| 工作记忆 | 当前任务目标、步骤、证据和临时结论 | 支持长任务、暂停和恢复 |
| 情景记忆 | 过去完成的任务、使用的证据、结果与反馈 | 避免重复研究，支持相似任务复用 |
| 语义记忆 | 经确认且长期有效的偏好、约束和事实 | 个性化回答与组织规则 |
| 流程记忆 | 哪类任务采用什么方法有效、何时失败 | 形成可复用研究模板和最佳实践 |

记忆写入应经过筛选：

- 是否具有长期价值；
- 是否得到证据或用户确认；
- 是否包含敏感信息；
- 是否有有效期；
- 是否与已有记忆冲突；
- 用户是否可以查看、修改和删除。

系统可以建立“经验候选”和“错误手册”，但只有通过规则或人工确认后，才能升级为长期记忆。

## 4.10 从答案升级为 Knowledge Studio

研究的终点不应只是一段聊天回答。Knowledge Studio 应把知识和证据转成可继续使用的成果。

### 文本成果

- 研究报告；
- 决策备忘录；
- PRD 和技术方案；
- 用户研究与项目复盘；
- FAQ、指南和培训材料；
- 会议纪要与周报。

### 结构化成果

- 对比表；
- 风险清单；
- 任务列表；
- 测试用例；
- 指标表；
- 时间线；
- 决策记录。

### 视觉与多媒体成果

- 知识图谱、流程图和架构图；
- PPT、信息图和数据图表；
- 音频概览；
- 带证据时间点的视频摘要；
- 培训课程和测验。

成果必须保持“活连接”：

- 每个重要结论可回到证据；
- 记录使用了哪些来源版本；
- 原始资料变化后标记可能受影响的段落；
- 用户可以刷新部分内容，而不是全部重生成；
- 人工修改得到保留，不被自动覆盖；
- 成果可以回流为新的知识对象，但需保留“生成知识”标签。

NotebookLM 的 Studio 证明了“基于来源生成多种成果”具有强产品价值；MMA-RAG 应进一步利用原生音视频证据，使成果不仅基于转写文本。

## 4.11 从一次上传升级为数据源与知识编译中心

产品需要区分三类接入方式。

### 一次性导入

适合本地文件、图片、音频和视频。

### 持续同步

适合企业文档、云盘、代码仓库、Wiki、RSS、网页、邮件和聊天系统。

### 实时查询或采集

适合数据库、业务指标、会议、屏幕录制和持续事件流。并非所有数据都要复制进知识库；实时数据可以按需查询并保存使用时快照。

### 统一身份、版本与血缘

同一份资料即使经历上传、同步、重新解析、生成摘要、建立 Wiki 或进入图谱，也应拥有稳定身份。用户需要能够看清：

- 当前看到的是哪个来源和版本；
- 哪些证据、页面和成果由它派生；
- 是否存在重复副本；
- 新版本替代了什么；
- 删除、撤权或过期后影响哪些派生内容；
- 任何索引都可以重建，而不会产生无法追溯的“幽灵知识”。

这一能力直接解决当前不同存储中知识库标识兼容的原型期问题，也是版本比较、权限传播和影响分析的前提。

上传和同步过程应从黑盒变成“智能导入向导”。

用户先看到系统识别和建议：

> 检测到扫描 PDF，建议启用视觉解析；检测到访谈音频，建议识别说话人、问题与观点；检测到演示视频，建议提取场景、操作步骤和错误状态。

用户选择处理目标：

- 仅用于搜索；
- 生成摘要和推荐问题；
- 编译 Wiki；
- 提取人物、事件和关系；
- 提取决策、需求和风险；
- 进行高保真多模态分析。

处理进度面向用户展示为：

```text
已接收
→ 正在理解内容
→ 正在建立证据
→ 正在创建索引
→ 正在编译知识
→ 正在质量检查
→ 可使用
```

用户可以查看失败阶段、重新处理、变更处理目标，并知道一次更新影响了哪些知识页面和成果。

## 4.12 建立通用 Agent 与工具中心

通用产品不应预先创建大量互相割裂的 Agent。第一阶段应以一个可靠的知识 Agent 加一组清晰工具能力为主，场景助手只是预设。

### 通用知识工具

- 语义搜索：寻找同义表达、相关概念和跨模态内容；
- 精确搜索：定位人名、错误码、数字、术语和原话；
- 结构浏览：先查看文档目录、视频章节、表格结构和来源元数据；
- 上下文展开：读取命中位置前后内容或完整来源；
- 比较版本；
- 搜索图片、音频片段和视频场景；
- 查询关系和时间线；
- 校验数字与证据；
- 查询网页或实时数据。

语义搜索、精确搜索、结构浏览和上下文展开应保持不同的用户语义。把所有能力隐藏在一个“万能搜索”中，会让 Agent 难以判断何时应该找相似内容、何时应该查原话、何时应该先理解资料结构。

### 通用行动工具

- 创建草稿；
- 更新知识页；
- 创建任务；
- 发送消息；
- 发起审批；
- 发布助手或成果；
- 设置监控和提醒。

### 场景预设

- 快速知识助手；
- 深度研究助手；
- 多模态分析助手；
- 数据分析助手；
- 知识维护助手；
- 自定义助手。

用户只需配置：

1. 助手负责什么；
2. 可以使用哪些 Space 和数据源；
3. 可以使用哪些动作；
4. 引用、质量和审批要求。

高级用户可以进一步配置工具和策略，普通用户不应看到 Top-K、RRF 权重或向量模型等技术参数。

### 工具契约与渐进发现

每个工具都应向产品明确声明：它能做什么、需要什么权限、是否会产生外部影响、预计耗时、失败后能否重试，以及结果会产生证据还是成果。

当工具数量增多时，不应把全部能力一次性交给模型和用户。系统先展示工具类别或 Skill 摘要，只有任务匹配后再加载详细能力。这样既减少选择噪音，也降低错误调用和上下文占用。

工具失败不应立即让整个任务丢失。系统应区分：

- 可以换参数再次尝试；
- 可以切换其他检索或数据来源；
- 需要用户补充信息；
- 需要审批；
- 权限拒绝，不允许绕过；
- 已取得部分结果，可以继续合成。

## 4.13 建立渐进式行动与审批

能力边界可以从“知道”扩展到“行动”，但要逐级开放。

| 风险级别 | 示例 | 默认产品策略 |
|---|---|---|
| 只读 | 搜索、打开、比较、计算 | 自动执行，保留轨迹 |
| 草稿 | 生成报告、Wiki 草稿、任务草稿 | 自动生成，用户确认后采用 |
| 低风险内部写入 | 更新个人笔记、保存证据集 | 可执行后通知，并支持撤销 |
| 正式知识修改 | 修改已发布页面、项目状态 | 展示差异并请求确认 |
| 外部影响 | 发送消息、公开发布、调用业务系统 | 明确审批和目标范围 |
| 高风险 | 删除数据、批量修改、敏感系统操作 | 二次确认、最小权限和完整审计 |

Agent 任务可以在审批点暂停，用户确认后从原位置继续，而不是重新执行整个研究过程。

## 4.14 建立空间、协作、权限和审计

从个人 Demo 走向通用知识平台，至少需要以下产品角色：

- 只读成员：浏览和提问；
- 内容贡献者：导入资料和维护自己创建的内容；
- 知识管理员：处理冲突、审核知识和管理质量；
- 空间管理员：管理成员、数据源、助手和发布渠道；
- 所有者：控制空间策略和高风险权限。

权限必须从来源贯穿到：

- 原始文件；
- 内容片段和多模态证据；
- Wiki 页面和图谱关系；
- 研究任务和成果；
- Agent 可用工具；
- 发布渠道和外部系统。

任何用户无权打开的内容，都不能通过摘要、Wiki、图谱、记忆或生成结果间接泄露。

审计中心应能回答：

- 谁访问了哪些敏感内容；
- AI 基于哪些资料生成了什么；
- 哪条知识由谁确认或修改；
- Agent 执行了什么动作；
- 谁批准了外部操作；
- 哪个来源变化导致了结论更新。

## 4.15 建立发布与开放能力

知识不应只存在于 MMA-RAG 的 Web 页面。发布中心可以面向：

- Web 工作台；
- 飞书等 IM；
- 网站嵌入助手；
- 分享链接；
- API；
- 浏览器扩展；
- MCP 资源和工具；
- 其他 Agent 或自动化系统。

发布对象不是简单复制一个聊天机器人，而是带有：

- 明确知识范围；
- 权限和身份；
- 可用工具；
- 回答与引用策略；
- 品牌和交互配置；
- 使用统计和反馈；
- 版本和下线能力。

## 4.16 将 OKF 作为知识可移植层，而不是内部知识模型

Open Knowledge Format（OKF）把 LLM Wiki 规范为可移植目录：Markdown 页面、YAML 元数据、标准链接，以及可选的索引、日志和引用。它最适合解决“知识如何被不同工具导入、导出和交换”，不适合替代 MMA-RAG 内部更丰富的多模态证据、权限、版本和任务模型。

建议提供“OKF-compatible Knowledge Package”：

- 支持导入 OKF 知识目录；
- 支持把某个 Space 或专题导出为 OKF；
- 为图片、音频、视频和原始文件保留资源清单与稳定引用；
- 导出 Wiki 页面、索引、变更日志和来源；
- 对无法表达的权限、区域、时间片段和质量信息使用扩展元数据；
- 未识别字段尽量保留，避免往返丢失；
- 明确导出的是知识快照，不等同于内部控制面。

预期收益：

- 降低知识被单一产品锁定的风险；
- 允许其他 Agent 和知识工具复用 MMA-RAG 的编译结果；
- 形成可共享、可归档、可版本化的知识包；
- 为开源社区建立扩展生态。

## 4.17 建立 Nexus Agent Harness：让自主研究成为可靠产品

进一步的 Harness Agent 调研揭示：Agentic 能力不能只描述“会规划、会调用工具”，还需要一套包裹在模型外部的运行保障。这里将它称为 **Nexus Agent Harness**。

它不是新的用户功能入口，而是保证所有深度任务具有一致行为的产品控制层：

```text
目标与范围
→ 任务计划
→ 工具与证据
→ 状态保存
→ 结果验证
→ 继续 / 暂停 / 审批 / 部分交付 / 结束
```

### 七项运行保障

#### 任务约束

每个任务都有步骤、时间、成本、模型调用和工具调用边界。系统还应检测相同搜索反复执行、连续没有新增证据和重复改写等无效循环。

#### 状态外置

目标、计划、范围、证据、成果、审批和停止原因不能只存在于模型对话里。用户刷新页面、网络断开或服务恢复后，任务仍能从最近的可靠进度继续。

#### 错误可观察

工具超时、来源不可用、参数错误和权限拒绝应成为结构化任务事件。Agent 可以针对可恢复错误换一种方法，但不能把权限拒绝当成普通失败绕过去。

#### 部分结果抢救

任务被取消、达到预算或某一步失败时，已经得到的证据、结论和草稿仍应保留。系统交付“已完成什么、还缺什么、为什么停止”，而不是只显示失败。

#### 上下文治理

长任务通过证据账本、稳定引用、去重和可追溯摘要控制上下文。摘要帮助继续工作，但任何最终事实都必须回到原始证据。

#### 行动安全

每项工具调用先经过权限、风险、审批和目标范围检查。外部网页、MCP 返回和用户上传内容都被视为可能包含不可信指令的数据，不能因此改变系统权限或行动策略。

任务恢复时也不能盲目重复外部动作。系统应先确认上一次发送、发布、创建或修改是否已经生效；状态无法确认时暂停并提示用户，而不是冒险执行第二次。

#### 结果验收

Agent 给出最终文本只是候选结果。系统还要判断目标是否完成、关键主张是否有证据、数字是否可核对、冲突是否披露，以及成果是否满足用户要求。

### 三级验证体系

| 验证层 | 核心问题 | 失败时的行为 |
|---|---|---|
| 契约验证 | 工具参数、输出结构、调用与结果是否匹配 | 修正参数、重试或换工具 |
| 策略验证 | 权限、审批、安全、预算和范围是否允许 | 拒绝、暂停或请求确认 |
| 结果验证 | 证据和最终成果是否真正满足任务目标 | 补检、修订、降级或部分交付 |

第三层最容易被忽略。相关性高不代表事实正确，有引用不代表引用支持主张，任务自然停止也不代表目标完成。

### 用户可见任务轨迹

用户不需要看到模型原始思维链，但应该看到结构化事实：

- 为什么选择快速或深入模式；
- 当前计划和已完成步骤；
- 调用了哪些能力以及耗时；
- 新增、重复和被排除的证据；
- 发现的冲突和缺口；
- 预算与预计剩余工作；
- 审批和人工修改；
- 最终状态与停止原因。

管理员还应看到跨任务的失败类型、恢复次数、工具健康度、成本分布和权限决策，从而区分“模型判断问题”“检索质量问题”“来源不可用”和“系统运行问题”。

## 5. 推荐的产品信息架构

### 5.1 顶层导航

#### 首页

展示最近变化、进行中的任务、待确认结论、知识问题、风险和与用户相关的洞察。

#### 知识空间

围绕项目、产品、客户、组织、研究主题或个人学习组织知识。

#### 提问与研究

统一承载快速问答、深度研究、历史任务和证据工作台。

#### Studio

从知识和证据生成报告、表格、图谱、PPT、音视频摘要和其他成果。

#### Agent 中心

管理助手预设、知识范围、工具权限、审批和发布。

#### 数据源中心

管理上传、连接器、同步、实时来源、处理进度和失败任务。

#### 治理中心

管理成员、权限、审计、知识健康、敏感信息、成本和质量。

普通用户可以只看到首页、空间、提问与 Studio；Agent、数据源和治理按权限渐进展示。

### 5.2 知识空间内部

一个 Space 建议包含：

- 概览：目标、主要知识、最新变化和风险；
- 来源：原始文件和数据源；
- 多模态素材：页面、图片、音频、视频、表格；
- Wiki：主题、人物、项目、概念、事件和分析页面；
- 关系：图谱、时间线和影响链；
- 结论：主张、支持、冲突和有效状态；
- 任务：正在进行和已完成的研究；
- 成果：报告、页面、图表、课程和发布内容；
- 问题：过期、冲突、缺失、重复和处理异常。

### 5.3 对话与研究页

推荐三栏布局。

#### 左侧：任务与会话

- 快速问答；
- 深度研究；
- 历史任务；
- 已完成成果；
- 置顶和共享内容。

#### 中间：目标、交流与进度

- 当前目标；
- 工作步骤；
- 阶段性发现；
- 已知限制；
- 待用户确认；
- 最终结果。

#### 右侧：证据工作台

- 多模态证据；
- 支持与冲突；
- 版本对比；
- 固定、排除和备注；
- 原文回看与播放。

## 6. 外部设计的正收益吸收方式

## 6.1 WeKnora

最值得吸收：

- 快速 RAG、ReAct Agent、Wiki 三种能力明确分工；
- Wiki 页面、链接、来源、版本、状态和知识问题；
- 处理设置、重新解析和可视化处理轨迹；
- 临时附件、推荐问题、引用抽屉和过程展示；
- 工作空间、角色、审计和多渠道发布；
- Wiki 与原始 RAG 交叉验证，发现冲突后进入修复流程。

不应照搬：

- 把大量解析、模型和检索参数直接暴露给普通用户；
- 让 Wiki 成为唯一入口；
- 默认构建所有图谱和页面；
- 把 MMA-RAG 的多模态优势降级成文档附属能力。

## 6.2 LLM Wiki

最值得吸收：

- ingest、compile、query、research、audit、librarian、artifact 的完整知识循环；
- 用链接和索引支持组合式研究；
- 通过审计和错误记录推动知识自我修正；
- 快速查询和深度研究分层；
- 研究结果可继续编译成知识和成果。

不应照搬：

- 将 Markdown 目录视为内部唯一存储；
- 把所有多模态信息压平成文本；
- 未经确认自动把研究推断发布成正式知识。

## 6.3 OKF

最值得吸收：

- 开放、轻量、工具无关的知识交换方式；
- 页面元数据、标准链接、索引、变更日志和引用；
- 对未知字段保持兼容，支持渐进扩展。

合理定位：

> 作为导入、导出、归档和互操作格式，而不是作为 MMA-RAG 的内部事实数据库。

## 6.4 RAGFlow

最值得吸收：

- 可编排且可复用的摄取流程；
- 解析和切分结果可视化、可人工干预；
- Agent 模板、记忆、发布和多渠道接入；
- 知识、Agent 和沙箱行动形成产品闭环；
- 对 GraphRAG、父子切片等能力按场景组合。

不应照搬：

- 把低代码流程画布作为所有普通用户的第一入口；
- 过早堆积大量垂直 Agent 模板；
- 让功能数量代替一致的知识对象和证据体验。

## 6.5 Dify

最值得吸收：

- 数据源、工具、模型、Agent 策略和触发器具有清晰的扩展边界；
- 知识处理流程可以草稿、调试、发布和复用；
- 数据源插件覆盖网页、在线文档和云盘；
- 多模态输出具有统一结构，便于扩展生态。

合理定位：

> 学习其扩展边界与插件产品化，不把 MMA-RAG 变成通用低代码应用平台。

## 6.6 NotebookLM

最值得吸收：

- 以来源为中心的问答和行内引用；
- Studio 将同一批来源转成多种学习和工作成果；
- 简单界面隐藏复杂研究过程；
- 用户可以围绕一个 Notebook 长期积累来源、笔记和输出。

MMA-RAG 可超越之处：

- 原生理解音频和视频内容，而不只依赖转写；
- 更细粒度的多模态证据；
- 组织级权限、活知识和行动闭环；
- 开放部署、模型和数据源生态。

## 6.7 GraphRAG

最值得吸收：

- Local Search 将实体关系与原文片段结合；
- Global Search 适合跨文档主题总结；
- 图谱可支持关系、多跳和全局视角。

合理定位：

> 只在关系型、全局型和复杂研究问题中启用，并始终回到原始证据核验。

## 6.8 Harness Agent 与持久运行时

DeerFlow、LangGraph、pi 和 OpenAI Agents SDK 补充了 WeKnora 之外的重要视角：可靠 Agent 的差异化越来越多地来自模型外部的任务保障。

### DeerFlow 2.x

最值得吸收：

- 把上下文压缩、工具错误、循环检测、预算、沙箱和权限控制作为统一运行保障；
- 长任务保留工作进度和部分结果；
- 工具与 Skill 按需发现，避免能力列表无限膨胀；
- 子任务隔离，只向主任务返回结构化结果和成果。

不应照搬：

- 面向通用 Super Agent 的 Shell、文件系统和多 Subagent 复杂度；
- 把自由执行能力默认开放给知识型任务；
- 让中间件数量本身成为产品能力目标。

### LangGraph

最值得吸收的是持久任务、暂停/恢复、人工确认和显式状态转换的设计思想。合理定位是“可替换的运行时参考”，而不是让产品对象和用户界面依赖某个框架术语。

### pi

最值得吸收的是“小核心、强扩展、完整历史、渐进压缩”的原则。压缩后的上下文可以帮助模型继续工作，但完整任务轨迹必须保留，用户也应能够回到任何关键节点查看或分支研究。

### OpenAI Agents SDK

最值得吸收的是工具审批、可序列化运行状态、会话、Guardrail 和统一 Trace。它再次说明审批和恢复必须是运行状态的一部分，而不是在 Prompt 中要求模型“记得先问用户”。

综合取舍：

> MMA-RAG 应建设自己的 Nexus Agent Harness 产品契约，底层运行时保持可替换；借鉴各项目经过验证的任务保障，不把多个 Agent Framework 同时叠加到业务层。

## 7. 明确的取舍清单

### 7.1 应优先采用

| 能力 | 净收益判断 | 原因 |
|---|---|---|
| Quick / Research 双路径 | 高 | 保留当前速度，同时提升复杂任务上限 |
| 持久化研究任务与证据工作台 | 高 | 直接解决复杂工作不可持续、不可复用问题 |
| Nexus Agent Harness 运行保障 | 高 | 让预算、停止、恢复、审批和结果验收不依赖模型自律 |
| 任务范围胶囊 | 高 | 防止跨知识库、跨会话和跨权限范围污染 |
| 原始证据 + 活知识双层 | 高 | 同时获得精确事实和结构化浏览能力 |
| Claim–Evidence 核验 | 高 | 显著提升可信度，是行动型 Agent 的前提 |
| 多模态原子证据 | 高 | 强化 MMA-RAG 最独特的竞争优势 |
| 能力画像与分层就绪 | 高 | 让高成本增强按需开启，并准确表达知识可用状态 |
| 证据账本与上下文治理 | 高 | 支撑长任务并减少重复信息、成本和摘要漂移 |
| 知识健康与版本影响 | 高 | 让知识从静态仓库变成长期系统 |
| Studio 与证据绑定成果 | 高 | 把回答转成真正工作产出 |
| 数据源同步与处理轨迹 | 高 | 提升新鲜度、可控性和企业可用性 |
| 空间、角色、权限和审计 | 高 | 通用组织场景和行动能力的底线 |
| OKF 导入导出 | 中高 | 成本可控，提升开放性和长期资产价值 |

### 7.2 应按需启用

| 能力 | 使用边界 |
|---|---|
| GraphRAG | 关系、多跳、全局主题；不用于所有精确查询 |
| 高成本页面视觉索引 | 复杂版面、设计稿和图表密集资料 |
| 深度视频理解 | 视频任务或高价值视频源，不对所有视频默认穷尽分析 |
| 网络研究 | 用户授权、内部知识不足或需要最新外部信息时 |
| 长期记忆 | 只有经过筛选、确认、有有效期的内容 |
| 行动工具 | 按风险逐级开放，并设置审批 |
| 工具/Skill 渐进发现 | 工具规模扩大后启用，首期保持少量语义清晰的工具 |
| 多 Agent 协作 | 只有独立权限、上下文或生命周期确实必要时 |

### 7.3 不建议作为近期重点

- 以“多 Agent 数量”作为 Agentic 的证明；
- 对所有知识库默认生成完整图谱；
- 把每次聊天自动写回正式知识；
- 让自动 Wiki 替代原始资料；
- 为展示前沿而默认调用最昂贵模型；
- 开放无审批的外部写操作；
- 一开始就追求覆盖所有企业连接器；
- 把低代码工作流画布置于普通用户主路径；
- 展示模型原始思维链；
- 把预算耗尽、循环停止或只获得部分结果包装成完整成功；
- 把会话摘要或 Wiki 摘要当作原始事实来源；
- 同时叠加多个 Agent Framework，让框架抽象渗透产品对象；
- 在没有回归评测的情况下重写现有检索链路。

## 8. 分阶段演进路线

每个阶段以用户可感知的结果和发布门槛结束，不以“完成若干模块”作为完成标准。

## 阶段 0：建立不可回退的质量与产品契约基线

### 目标

证明升级不会损失当前多模态和检索能力，并先统一 Evidence、Task、Scope、Claim、Artifact 和任务结果状态的产品语义。

### 用户可感知结果

- 现有快速问答体验保持；
- 文档、图片、音频、视频的检索与引用能力不退化；
- 可以明确比较升级前后的质量、速度和成本；
- 用户能够分辨原始资料、AI 提取、AI 生成和人工确认内容。

### 发布门槛

- 为四种模态建立代表性查询集；
- 覆盖单库、跨库、文件限定和自动路由；
- 检索召回、排序、引用定位和回答支持都有基线；
- Fast Path 的关键质量不得下降；
- 新能力可独立开关和灰度；
- 任务范围、证据和结果状态有统一表达。

## 阶段 1：可恢复的知识任务底座

### 目标

先让系统能够可靠承载长任务，再增加更强的自主规划。避免先做会思考的 Agent，却无法在刷新、断线、取消、审批或故障后继续。

### 核心产品能力

- 持久化 Task、范围、步骤、证据和成果；
- 暂停、恢复、取消、重试和断线续看；
- 任务范围胶囊与权限快照；
- 时间、成本和工具预算；
- 结构化任务事件和停止原因；
- 部分结果保留；
- Fast Path 与任务模式互不干扰。

### 验收场景

- 页面刷新或服务恢复后任务状态不丢失；
- 用户可以暂停、继续和取消；
- 取消或预算用尽后仍能查看已有证据与草稿；
- 当前知识范围、外部工具权限和任务消耗始终可见；
- “部分完成”“证据不足”“等待审批”和“失败”不会被包装成成功。

## 阶段 2：可信的 Agentic Research

### 目标

把“复杂问题需要用户手动多轮追问”升级为“系统可以完成持续研究并验收结果”。

### 核心产品能力

- L0–L3 自适应执行深度；
- 计划、搜索、精确查找、结构浏览、上下文展开和版本比较；
- 证据账本与上下文去重；
- 证据覆盖判断、冲突检测和补充检索；
- 主张级验证；
- 阶段性进度、限制和部分结论；
- 研究报告成果。

### 验收场景

- 跨多个文档和模态解释一次变化；
- 对两个版本进行证据化比较；
- 首轮证据不足时主动继续检索；
- 来源冲突时明确展示分歧；
- 无新增证据时能够停止，而不是重复循环；
- 关键主张均被支持、反驳或标记证据不足；
- 简单问题仍走原 Fast Path。

## 阶段 3：原生多模态证据与活知识层

### 目标

让资料从“可搜索文件”变成“可精确核验、可浏览、可连接、可演化的多模态知识”。

### 核心产品能力

- 多模态证据卡；
- 页面、区域、单元格、说话人时间片和视频场景级定位；
- 自动 Wiki 和知识对象；
- 页面链接、反向链接、版本和状态；
- 人物、项目、概念、事件、决策、风险和指标页；
- 图谱和时间线视图；
- Knowledge Space 能力画像与分层就绪状态；
- 知识问题、AI 修复草稿和人工审核；
- 原始资料、提取知识、生成知识和确认知识分层。

### 验收场景

- 新资料能进入已有主题而不制造大量重复页面；
- Wiki 中的关键结论可以回到多模态原始证据；
- Agent 可以直接比较图片区域、音频片段和视频场景，而非只消费文字摘要；
- 原文与 Wiki 冲突时以证据为准并产生问题；
- 新版本到达后，旧结论和相关成果收到影响提示；
- 用户不通过聊天也能理解一个 Space 的人物、事件和核心结论。

## 阶段 4：Knowledge Studio 与知识复利

### 目标

把研究结果变成可复用成果，并让每次工作反哺知识系统。

### 核心产品能力

- 报告、对比表、时间线、图谱、PPT、课程和音视频概览；
- 成果与证据、版本和状态保持连接；
- 资料变化后的局部刷新和影响分析；
- 知识馆员、缺口检测、经验候选和错误手册；
- OKF 导入、导出和知识包；
- 成果共享与协作审核。

### 验收场景

- 一份研究可以输出多种成果，而不重复完成资料搜集；
- 成果中的结论可以逐条核验；
- 来源变化时能指出具体受影响段落；
- 人工修改不会被刷新过程无痕覆盖；
- Space 可以导出为可理解、可迁移的知识包。

## 阶段 5：组织级行动与开放生态

### 目标

让可靠知识在权限内推动工作，而不是停留在阅读和生成。

### 核心产品能力

- 持续同步数据源；
- 通用工具、Skill 渐进发现和 MCP 接入；
- 草稿、任务、消息、发布和监控动作；
- 分级审批、撤销和审计；
- 空间角色、来源权限继承和外部协作者隔离；
- Web、IM、Widget、API 和其他 Agent 发布。

### 验收场景

- 研究结果可以转换成待确认任务和文档草稿；
- 高风险动作必须暂停并等待审批；
- 外部来源中的不可信指令不能改变系统权限和行动策略；
- Agent 无法越权读取或泄露来源内容；
- 每次知识修改和外部动作可以追溯；
- 同一知识助手可以安全发布到多个渠道。

## 阶段 6：主动知识系统

### 目标

让系统主动维护知识质量、识别变化和发现下一步机会。

### 核心产品能力

- 新资料触发影响分析；
- 主动发现高价值知识缺口；
- 识别即将过期或单点掌握的知识；
- 跟踪研究建议和行动结果；
- 根据用户反馈改进研究策略；
- 在预算、权限和频率限制下运行知识维护任务。

### 验收场景

- 系统能在用户提问前发现关键冲突或过期内容；
- 主动提醒包含明确证据和影响范围；
- 用户可以控制频率、范围和通知方式；
- 低价值提醒得到抑制，避免“主动噪音”。

## 9. 评价体系

### 9.1 北极星指标

建议采用：

> **可信知识任务闭环率**

定义：用户发起的知识任务中，完成了“找到充分证据 → 形成可核验结论 → 交付可使用成果或下一步”，并且未发生权限、引用或重大事实问题的比例。

这个指标比“回答次数”“上传文件数”更能反映 Agentic 知识库的真实价值。

### 9.2 不可回退指标

- 各模态 Recall@K、nDCG、MRR；
- 自动路由准确率；
- 页面、区域、时间点定位准确率；
- Fast Path 响应时间；
- 引用可打开和可播放率；
- 单次快速问答成本。

### 9.3 Agentic Research 指标

- 复杂任务成功率；
- 多跳问题完成率；
- L0–L3 执行深度选择准确率；
- 证据不足时继续查找的正确率；
- 无效研究步骤和重复调用比例；
- 每一步新增有效证据的比例；
- 无新增证据时正确停止率；
- 任务暂停/恢复成功率；
- 任务状态与事件恢复完整率；
- 停止原因分类准确率；
- 失败或取消后的部分结果可用率；
- 任务范围污染率；
- 达到可信结论所需时间与成本；
- 用户接管和人工修正次数。

### 9.4 可信度指标

- Claim 支持率；
- 引用精确率和完整率；
- 冲突发现率；
- 过期知识识别率；
- 正确拒答率；
- 数字复核通过率；
- 高风险结论人工确认率。

### 9.5 知识健康指标

- 有来源知识比例；
- 已确认知识比例；
- 孤立、重复和冲突页面比例；
- 过期知识平均发现时间；
- 新来源到知识可用的时间；
- 从“可搜索”到“已增强/已编译/已验证”的各阶段耗时与成功率；
- 知识问题修复率；
- 来源变化后的影响覆盖率。

### 9.6 用户价值指标

- 从问题到首个可信结果的时间；
- 从资料到可交付成果的时间；
- 研究任务复用率；
- 证据和知识对象复用次数；
- 重复提问减少比例；
- 人工查找和整理时间下降比例；
- 成果被采用、分享或转成行动的比例。

### 9.7 安全与治理指标

- 权限泄露率；
- 越权工具调用率；
- 外部内容诱导越权或改变策略的成功率；
- 审批遵循率；
- 可撤销动作比例；
- 审计覆盖率；
- 敏感内容错误发布率。

## 10. 关键产品风险与防护

### 风险一：Agent 让简单问题变慢、变贵

防护：保留 Fast Path，复杂度自适应，允许用户选择速度或深度，Research 设置预算和停止条件。

### 风险二：自动 Wiki 制造新的错误知识

防护：原始证据不可被无痕修改；生成知识明确标识；关键结论主张级引用；发布和合并需要质量门槛。

### 风险三：多模态被再次压缩成文本

防护：将页面、区域、片段、场景和时序设为一等证据；在检索、验证、引用和成果中保留原始媒体入口。

### 风险四：GraphRAG 成本高、错误难发现

防护：按需启用；图谱关系必须能回到证据；先服务高价值关系型问题，不追求全量图谱覆盖。

### 风险五：长期记忆污染

防护：只保存长期价值、可确认、有权限和有效期的内容；提供查看、修改、删除和冲突处理。

### 风险六：主动能力变成噪音

防护：以影响范围、严重程度和用户关注度排序；支持订阅、静默和反馈；主动提醒必须带证据和建议动作。

### 风险七：连接器和工具扩大攻击面

防护：最小权限、来源权限继承、工具范围、审批、审计、凭证隔离、输出检查和安全沙箱；外部网页、MCP 结果和上传内容始终按不可信数据处理，不能借其中的指令提升权限。

### 风险八：功能太多导致产品复杂

防护：统一入口、自动模式、场景预设、渐进式设置；普通用户围绕 Space、Task、Evidence 和 Artifact 工作，不接触底层参数。

### 风险九：任务停止被误判为任务成功

防护：把结果验收独立于模型停止；所有任务记录完成度和停止原因；预算、证据不足、取消和部分完成使用不同状态。

### 风险十：长上下文压缩造成事实漂移

防护：完整轨迹和证据账本长期保留；摘要只承担工作恢复，不承担事实证明；最终主张重新绑定原始证据。

### 风险十一：派生能力状态不一致

防护：明确区分可搜索、已增强、已编译、已验证和已发布；Wiki、图谱或媒体增强失败不应让基础资料不可用，也不能把未完成状态显示为全部完成。

## 11. 升级完成后的典型体验

### 场景一：简单事实问答

用户问：“最新方案的发布日期是什么？”

系统走 Fast Path，快速给出日期、来源页和更新时间。如果多个版本冲突，展示最新有效版本和历史变化。

### 场景二：跨模态深度研究

用户要求：“结合评审纪要、设计稿、访谈录音和操作录像，分析流程为什么被修改。”

系统创建研究任务，查找相关版本、会议片段、访谈原话、设计变化和失败操作；发现证据不足时继续搜索；最终输出原因、时间线、争议、证据和建议。

### 场景三：活知识维护

新版文档进入 Space 后，系统发现三条已确认结论需要更新、两份成果可能过期、一段培训视频仍在描述旧流程。知识管理员查看差异并决定更新、保留争议或归档。

### 场景四：成果与行动

用户把研究结果生成决策备忘录和 PPT，再将建议转成任务草稿。系统展示负责人建议、依赖和证据；用户确认后才写入外部系统。

### 场景五：开放知识包

用户把一个专题导出为 OKF-compatible 知识包，包含 Wiki、索引、变更日志、来源和多模态资源清单；其他知识工具可以导入并继续研究。

### 场景六：长任务中断与部分交付

一项深度研究在运行中达到预算上限。系统没有生成一份假装完整的报告，而是保存已确认结论、候选证据、尚未解决的问题和停止原因。用户可以缩小范围、补充预算或从同一位置继续，不需要重新研究已经完成的部分。

## 12. 最终产品形态

升级后的 MMA-RAG 应同时扮演七个角色：

1. **多模态记忆系统**：保存文字、页面、图像、声音、视频、数据和它们的历史；
2. **证据系统**：让每条重要结论都能回到精确原始位置；
3. **活知识系统**：把资料编译为可浏览、可连接、可演化的知识；
4. **自主研究系统**：围绕复杂目标持续查找、比较、验证和调整；
5. **知识生产系统**：把证据和结论转成可复用成果；
6. **可控行动系统**：在授权和审批下推动后续工作，并从结果中学习；
7. **可靠运行系统**：让长任务具备范围、预算、恢复、部分交付、验收和审计能力。

一句话概括最终目标：

> **让任何个人或组织都能把分散的文档、图片、声音、视频和数据，变成一个会研究、能核验、可演化、会产出并可安全行动的第二知识系统。**
